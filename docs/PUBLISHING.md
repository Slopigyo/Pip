# First public GitHub publication

This checklist prepares a **source-code portfolio**, not a hosted service, packaged app, or model distribution. The local documentation and workflow do not create a GitHub repository, publish commits, enable account settings, or promise passing CI.

Model replies still cannot supply this metadata, and evidence checks and explicit acceptance are unchanged.

Coverage includes older proposals without the field and rejection of duplicate, out-of-range, negative, boolean, float, and string indices. These checks used synthetic data and providers, not a real model or workspace.

For the first public push, the broader deterministic Python suite also passed: **268 tests**. Previously passed checks included **37 mocked speech UI tests** and syntax checks for the two application JavaScript files; those unrelated local checks were not repeated. These are local preparation results; check the repository's **Actions** tab for current hosted CI status. Passing tests are not a security audit, model-quality benchmark, or claim that all workflows currently work.

## Before the first push

- [x] Fix the proposal-schema blocker and verify the affected flows with focused regression tests.
- [ ] Review the full CI result and report any remaining failures honestly before calling the overall suite green. Keep this validation status current.
- [ ] Read the [Apache-2.0 license](../LICENSE) and [dependency inventory](DEPENDENCIES.md). The grant covers project-authored material, not external models, datasets, subscription access, or every future bundled binary.
- [ ] Review the exact files to be committed. Include source, tests, documentation, license, and workflow—not the private original archive, workspace databases, real résumés/audio, exports, model assets, environment files, or build output. Do not force-add ignored files.
- [ ] Review reachable Git history as well as the working tree. A focused local review found no confirmed live credentials or private workspace/archive payloads in the inspected tracked history; it was not an exhaustive security audit. Commit author/committer names and email addresses, and earlier developer-home browser paths, remain visible in history. Current-file cleanup does not remove them. Decide whether those ordinary metadata are acceptable before publishing; history rewriting requires a separate deliberate decision.
- [ ] Choose the desired public Git author identity for future commits. GitHub can supply a noreply address; changing configuration does not change earlier commits. Never publish access tokens or sign-in credentials in the remote URL.
- [ ] Review any screenshot/video using [the synthetic demo guide](PORTFOLIO.md). Avoid address bars, startup tokens, desktop notifications, personal filenames, and real profile content.
- [ ] Commit the reviewed preparation changes. Version `0.2.0` remains the prototype milestone; repository documentation alone does not require a version bump.

Useful read-only review commands from the repository root:

```powershell
git --no-pager --no-optional-locks status --short
git --no-pager diff --check
git --no-pager diff --cached --stat
git --no-pager diff --cached
git --no-pager log --format=fuller
```

Untracked files do not appear in `git diff`, so inspect their contents before staging. Ignored files and unreachable/reflog objects were outside the focused history review; do not upload a whole workspace folder as a substitute for a reviewed Git push.

## GitHub settings and publication

1. Choose the owner, repository name, and exact remote URL. Keep the source package/storage identifiers unchanged even if the public repository uses Pip in its name.
2. Create an empty repository without an autogenerated README, license, or ignore file, since those are already supplied. Starting private gives time to inspect the rendered docs and Actions results before choosing public visibility; verify your account's private Actions allowance if using that route.
3. Add the confirmed remote and push only after reviewing the local commit set. This checklist intentionally does not supply a guessed owner/URL or execute a push.
4. Inspect the rendered README and the first Actions result. If CI fails, report/fix the failure rather than disabling the check or adding a success badge prematurely. GitHub usage and billing settings belong to the owner's account, separate from the project's Apache license.
5. Enable **private vulnerability reporting** if the repository/account makes it available. Confirm the reporting route in [SECURITY.md](../SECURITY.md); add a real private contact only if you choose to maintain one. Enable available dependency alerts, secret scanning, and push protection; do not assume the workflow enables these settings.
6. Add a short description, relevant topics, and optionally pin the repository on your profile. For example: “Local-first personal exploration prototype with reviewed AI insights, résumé intake, and local dictation.” Do not describe it as a production job-search service.
7. Choose public visibility when satisfied. A tagged release or binary installer is optional and should wait for a verified checkpoint; do not automatically tag the current baseline as a stable public release.

Outside contributors can use [CONTRIBUTING.md](../CONTRIBUTING.md). No elaborate governance, CLA service, public server, or app-store release is needed to show a credible work-in-progress portfolio.
